## Findings

**F1 — P2 (should fix; not blocking on its own).** `ds/net.py:69-72` — `os.killpg(proc.pid, SIGKILL)` runs unconditionally in `run_command`'s cleanup, including after `communicate()` has already reaped the child normally.
*Trigger:* every successful call — i.e. `sudo … distractions-nft`, `systemctl --user start`, `xdg-settings get`, `update-desktop-database` in each 60 s reconciliation, plus `open`'s `_default_browser_id` and setup's `_xdg_settings`.
*Impact:* after the leader is reaped its PID is free; a reused PID that is a new session leader belonging to the same user would be killed with SIGKILL (blast radius: user processes, e.g. a just-launched browser scope). Probability is low (needs PID wrap in a microsecond window), but this is exactly the hazard fn-27.3's Fable gate classed as a defect and fixed in `distractions-nft:219-223` with `test_successful_listing_does_not_signal_reaped_pid`. The two runners now disagree on discipline.
*Correction:* gate the SIGKILL/`communicate` teardown on `proc.returncode is None` (mirror the wrapper), and add a `killpg`-not-called-after-success regression in `tests/test_net.py`. Cheap and well-scoped for the fn-27.2 gate window.

**F2 — P3.** `ds/listener.py:97-99` — when `cgroup.ensure_slice()` fails or times out, `_apply` short-circuits to `unavailable` and emits `net._notice_unavailable()`, whose text is "Wrapper missing or sudo -n distractions-nft refused." The wrapper was never invoked. Previously the wrapper was the check (old docstring). *Impact:* misleading one-shot notice; `state.json`/health themselves are truthful (`unavailable`). *Correction:* a slice-specific notice or a `why` parameter on `_notice_unavailable`.

**F3 — P3.** `ds/listener.py:66` — `_ask` renders every `error` reply as "The listener rejected the request." With fn-27.1's aggregate semantics, `reload`/`refresh` now also answer `error` when config reload and firewall apply succeeded but only the desktop-cache step failed or the tool is missing (`setup.py:1032-1036,1086-1090`). *Impact:* CLI exit 1 with a message implying the reload was refused; the menu path is unaffected because `config.update` ignores `request_reload`'s reply. *Correction:* either a distinct reply token for "applied, launcher cache failed" or message text that says the request completed with a launcher-cache failure.

**F4 — P3 (carried from fn-26.1 review, still open at head).** `ds/state.py:217` `PING_TIMEOUT = 0.2` vs. on-loop synchronous work that survived fn-27: `hold.push` (busctl, `IPC_TIMEOUT = 10`) forced every period (`listener.py:473`), `hyprctl` per tick/event, `_scan` on reload. The bar now probes on every `state.json` write and every 30 s, so a probe landing inside those calls yields a transient "degraded: Listener did not respond" dot — the opposite of the spec's "quiet indicator". The offline suite only proves ping within 1 s (`_reload("ping", timeout=1)`), not 0.2 s. No runtime evidence either way; flagged as design risk, not a defect. Raising to ~1 s or moving `hold.push` off-loop are both contract-compatible.

**Docs (pending final pass — noted, not counted):** `docs/internals.md` state table shows `launcher_refresh: "ok"` but does not enumerate `off/ok/unavailable/deferred`; `_reload_wait()` is now ~255 s worst case for `reload`/`refresh` clients and README still implies a quick round-trip; both belong to fn-26.2.

**Non-issues checked and dismissed:** `.flow/evidence/` is a committed artifact consistent with committed `.flow/reviews`; `DS_CGROUP_ROOT` in the wrapper is the pre-existing pattern and sudo `env_reset` strips it; lazy `from ds.net import run_command` imports avoid the `net↔setup` cycle; `_V3_LABELS` keys do not duplicate `_BOOL`; menu indices 4/5 match tests; `/bin/bash` trampoline `$$` semantics are validated by live evidence and the exec-chain test.
