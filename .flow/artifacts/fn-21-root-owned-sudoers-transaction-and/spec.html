01

Thesis

scope: business

A marketplace reviewer stopped the listing review of commit 1c3fa25 and named four boundaries the plugin does not hold as tightly as its design claims. One of them is a real local-escalation window on the author's machine today: the sudoers drop-in that grants passwordless root to the nft wrapper is validated as the user, then re-opened by pathname when root installs it. The other three are unbounded reads that a granted account, or a hostile state file, can drive.

The load-bearing clarification: the reviewer specified the required shape rather than leaving it open, so no design question blocks the work. Validation and activation become one root-owned, descriptor-pinned transaction with revalidation immediately before an atomic rename. Everything else here is a cap.

03

Architecture

four surfaces · confirmed at 1c3fa25

Setup transaction

Now: renders the grant to a user-owned temp file, validates it with visudo, then hands the pathname to a sudo helper that re-opens it.

Target: root writes, root validates, root renames. The name is resolved once.

Wrapper install

Now: root copies the helper out of the user-writable plugin directory by pathname.

Target: a pinned, no-follow source descriptor carries the bytes that were checked.

Privileged nft helper

Two argv forms, one fixed table, every address validated with ipaddress.ip_address. The ruleset shape is confined; the count is not.

Target: a byte cap and an address cap, refused before allocation and before commit.

Bar watcher and hold claim

The widget holds a watching FileView on the state path for the life of the shell. Summary take renames held.jsonl to a private claim, then reads all of it.

Target: a regular-file check and a size cap on both reads.

04

Edge cases and constraints

grouped by blast radius

Privilege

  • A denied, cancelled, or non-TTY sudo fails closed and leaves no half-installed grant.
  • A rejected grant leaves any prior grant intact.
  • No new privileged command and no widening of the one-line policy.

Usability

  • The transaction stays one interactive prompt. Two prompts trade a security win for a regression the earlier privilege work avoided.
  • A re-run whose wrapper bytes and grant already match still skips the prompt.

Runtime and process

  • The bar renders its empty state on irregular, oversized, or unreadable state rather than blocking the shell.
  • An over-cap claim file is truncated at a record boundary; the claim already removed it, so the records cannot be re-read.
  • main stays frozen at 1c3fa25 until the fix lands, because validation binds to the HEAD at filing.

Boundaries

scope: business

Is

  • How bytes are validated on the way to root.
  • How much any one read materializes.
  • Regression tests for each new refusal.
  • A revalidated listing issue and a posted reply.

Is not

  • Any change to blocking behavior, the site list, the banner path, or summary content.
  • The baseline's citations of .flow/ planning files, already answered in the maintainer note.
  • Filing or arguing the listing decision.
  • New dependencies or a wider sudoers policy.
06

Decision context

scope: both
D1 · sudoers activation shape

Chosen: one root-owned, descriptor-pinned transaction with revalidation immediately before an atomic rename.

"Validation and activation must be one root-owned, descriptor-pinned transaction with immediate revalidation before atomic rename; apply the same no-follow/pinned-source treatment to the wrapper copy." — reviewer, issue #4518

Rejected: the current user-side temp file plus a root copy by pathname; and a narrower fix that only tightens the temp file's permissions, which leaves the same-UID window open because the file is owned by the account that would attack it.

D2 · ordering

Chosen: the sudoers transaction leads. It is the only finding that crosses a privilege boundary.

Rejected: leading with the caps. They close resource-exhaustion surfaces the granted account already reaches, at lower severity and far lower design risk.

Parked unknowns

2 open
  • Can Quickshell's FileView express a size or regular-file bound directly, or must the bar reach the state through a bounded reader? Resolved by reading the FileView API surface in the installed Quickshell version against what the widget needs.
  • The concrete cap values for the wrapper's input and for the two bounded reads. Resolved by measuring the sizes the listener and the hold file produce in normal use and setting each cap above that with headroom.
